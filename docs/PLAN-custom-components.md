# 完整自定义元件接口目标计划书

更新时间：2026-09-20

## 1. 目标

把当前“固定引脚 + C++ 逻辑回调”的原生元件能力，扩展成一套可以承载普通逻辑、状态元件、
复合电路和交互外设的稳定接口。完成后，Mod 作者不需要直接访问游戏对象、固定 RVA、OpenGL
状态或 Nim 内存布局，也能实现和原版元件同等级别的：

- 仿真行为；
- 棋盘内外观；
- 鼠标、键盘和焦点交互；
- 每实例状态与存档；
- 属性编辑、复制、撤销和重做；
- 原版元件逻辑、绘制与外设行为复用。

本计划以两个参考元件作为最终闭环：

1. **自定义 Keyboard**：能够获得实例焦点、消费键盘输入，并通过输出脚把按键状态和字符送入电路；
2. **自定义 Screen**：能够接收电路数据，在棋盘上的元件本体内显示 framebuffer，并正确保存配置、
   释放资源和处理重载。

“完整”不表示允许任意 DLL 不受限制地调用游戏内部函数，而是指公开契约已经覆盖原版常见元件所需的
逻辑、状态、绘制、输入和持久化能力。特殊平台能力仍应通过显式、可协商的设备服务提供。

## 2. 当前基线

| 能力 | 当前状态 | 主要缺口 |
|---|---|---|
| 类型注册 | `TCNativeComponentDefinition` 可注册稳定 ID、名称、说明、SVG、引脚和回调 | 只有一种实现形态；没有类型查询、分类、依赖和原版行为别名 |
| 引脚 | 每方向 1–8 脚，每脚 1–64 位，总输入不超过 128 位 | 不能表达零输出 Screen、零输入源、动态引脚或多字信号 |
| 仿真 | `RESET` / `REFRESH` / `CYCLE`；每实例 `state[8]` | 固定数组、固定状态、字宽输出依赖预留状态槽，不能调度唤醒 |
| 电路复用 | 可导入 `circuit.data`，内部原版元件由游戏执行 | Prototype 克隆只复制数据，不复制特殊行为、绘制和交互 |
| 实例生命周期 | 编译期 token 与 `instance_id` 可区分实例 | 没有稳定实例句柄和创建、销毁、复制、移动、保存回调 |
| 棋盘绘制 | SVG 外形；Mod 可画主菜单页面和侧栏 | 没有附着于元件实例的棋盘绘制上下文 |
| 输入 | 插件 UI 可读键盘、鼠标和字符输入 | 没有元件命中测试、实例焦点、事件消费和线程桥 |
| 状态与存档 | Mod 有 `plugin-data/<id>/`；电路保存自定义 ID | 没有每实例配置/状态 blob、迁移、缺失 Mod 占位 |
| 编辑器集成 | 可以放置自定义元件 | 删除、移动、配置、动态引脚、单步撤销分组尚不完整 |
| 外设 | 可在侧栏画图、上传纹理 | 没有 framebuffer、实例化键盘服务、GPU 生命周期 |

现有接口和兼容行为必须保留；新能力通过 `query_service` 返回独立版本化服务，不继续无限扩展
`TCHost` 尾部，也不原地改变 `TCLogicIO` 或 `TCNativeComponentDefinition` 的布局。

## 3. 完成标准

满足以下全部条件后，才把目标标记为完成：

1. 元件允许 0 个输入或 0 个输出，引脚使用稳定 ID，数值不再受固定 8×64 位数组限制；
2. 每个实例有世代检查句柄和完整生命周期，实例销毁后旧事件、旧资源和旧句柄全部失效；
3. 组合逻辑、状态逻辑、内部复合电路和原版别名四条路径均有真机验证；
4. 状态与配置由宿主管理，支持复制、撤销、重做、存档、载入和版本迁移；
5. 元件能够在棋盘本体上绘制，并得到局部坐标、裁剪、缩放、旋转和可见状态；
6. 元件能够安全获得鼠标、键盘、字符和 IME 输入，并按实例管理焦点和事件消费；
7. 仿真线程和渲染线程通过有容量、可失效的宿主消息通道通信，不共享悬空指针；
8. 原版元件可以按稳定语义 ID 查询，并能选择“只复制元数据”“作为内部节点”或“完整行为别名”；
9. 自定义 Keyboard 和自定义 Screen 的自动真机用例通过；
10. SDK 头、ABI 快照、文档、限制表、诊断、示例和发布说明成套完成。

## 4. 设计原则和红线

- **证据先于契约**：原版 Keyboard/Screen 的仿真、绘制、输入、保存入口必须先由只读探针和真机行为
  核实，再写入稳定接口。
- **句柄代替长期裸指针**：Board、实例、Surface、资源和消息都带所有者与 generation。
- **线程职责不混用**：仿真回调不调用 UI/GPU；渲染回调不直接修改仿真状态。
- **宿主拥有跨线程队列和资源**：插件只提交值、命令或快照，宿主负责失效、限额和销毁。
- **保存未知数据**：缺少 Mod 或版本过新时保留元件占位和原始 blob，不能静默丢失玩家电路。
- **原版复用分层**：克隆外观、组合内部电路和完整原版别名是三件事，接口和文档不得混称。
- **失败可诊断**：每次拒绝都要能说明是版本、线程、状态、配额、依赖还是游戏构建不支持。
- **向后兼容**：旧 Mod 继续走现有接口；新 Mod 必须显式查询所需服务和版本。
- **不绕过游戏规则**：是否允许自定义元件、关卡计分和成就策略继续由游戏/宿主决定。

## 5. 目标服务划分

| 服务 | 职责 | 优先级 |
|---|---|---|
| `tc.component.registry` | 类型注册、元数据、实现类型、能力和依赖查询 | 必须 |
| `tc.component.geometry` | 尺寸、引脚锚点、旋转、碰撞和坐标变换 | 必须 |
| `tc.component.instances` | 稳定实例句柄、生命周期、配置和状态所有权 | 必须 |
| `tc.component.simulation` | 可变长输入输出、阶段、调度、原子提交 | 必须 |
| `tc.component.storage` | 配置/状态序列化、迁移、占位、复制和撤销快照 | 必须 |
| `tc.component.compose` | 内部节点、嵌套元件、原版查询和完整别名 | 必须 |
| `tc.component.render` | 棋盘本体、预览、图标和覆盖层绘制 | 外设必需 |
| `tc.component.input` | 命中、鼠标、键盘、IME、焦点和事件消费 | 外设必需 |
| `tc.component.channel` | 仿真线程与渲染线程之间的消息和快照 | 外设必需 |
| `tc.device.keyboard` | 实例化键盘状态、事件队列和字符编码 | Keyboard 验收必需 |
| `tc.device.framebuffer` | Surface、像素上传、脏矩形和棋盘绑定 | Screen 验收必需 |
| `tc.component.editor` | 属性、上下文菜单、调整尺寸和 Undo 集成 | 完整体验必需 |

各服务独立协商版本。元件只声明实际依赖，例如普通 AND 不应因为没有 framebuffer 服务而加载失败。

## 6. 类型、引脚和实现模型

### 6.1 类型定义 V2

新增 `TCComponentTypeDefinitionV2`，至少包含：

- `size`、定义版本和存档 schema 版本；
- 由 Mod 命名空间约束的稳定 `type_id`；
- 名称、说明、本地化 key、分类、标签和排序；
- 图标、SVG、默认尺寸和旋转能力；
- 门数、声明延迟和有状态标志；
- 所需服务、所需 Mod、所需其它元件类型；
- 实现类型及对应实现描述；
- 生命周期、仿真、绘制、输入、存储和编辑器回调表。

实现类型至少支持：

| 类型 | 语义 |
|---|---|
| `NATIVE_CALLBACK` | 输入值交给插件回调，输出由插件产生 |
| `COMPOSITE` | 宿主构造或导入内部网表，由游戏编译执行 |
| `BUILTIN_ALIAS` | 保留原版仿真、绘制、输入和保存行为，仅覆盖允许覆盖的元数据/默认配置 |
| `PLACEHOLDER` | 缺少定义时由宿主生成，不参与仿真但保留引脚、配置和状态 |

### 6.2 引脚定义 V2

新增稳定 `pin_id`，支持：

- 0 到协商上限个输入/输出；
- 固定位宽、自动位宽和范围位宽；
- 超过 64 位的多字信号；
- 引脚局部坐标、侧面和标签布局；
- 默认值、可选连接、时钟/复位/使能等语义；
- 固定引脚与根据配置生成的动态引脚。

动态引脚只能通过宿主的配置事务修改。宿主必须先计算会断开的导线、征得编辑流程确认、写入一条
撤销记录，再重建引脚和触发编译；插件不得直接改棋盘容器。

### 6.3 数值表示

**2026-09-22 取舍（已定，见 [research/custom-component-pins.md](research/custom-component-pins.md)）**：
游戏原版自己的信号上限是 64 位，而实测证明生成代码里的外调**只能可靠地传 4 个参数**
（扩到 6 个参数时第 5、6 个参数收到的是垃圾）。因此：

- **每脚 1–64 位，不做多字（>64 位）信号**；本节原先的"带字节长度的多字视图"从首版范围移除；
- **总输入预算固定 128 位**（两个 payload 字）：脚数可以超过 8，但脚数 × 位宽之和 ≤128 位；
- 需要更多位的元件（例如 1+64+64 的 64 位加法器）由 M2 的宿主状态/缓冲路线解决，
  而不是扩外调形状（输出侧的 `0x9a0000` 状态槽已经在用同样的做法）。

于是 V2 的值表示是：每脚一个 `uint64_t`，加宿主借用的脚数组（脚数可 >8），
固定 `uint64_t inputs[8]` 的旧结构只保留给 V1：

- 小于等于 64 位时提供快速访问器；
- 输出一次回调结束后原子提交；
- 未写输出、越界写、宽度不符都有确定错误；
- `REFRESH` 不能提交持久状态。

## 7. 实例、状态和生命周期

### 7.1 实例句柄

`TCComponentInstanceHandle` 至少带：对象种类、所有者、实例 ID、generation 和保留字段。接口应支持：

- 验证句柄；
- 读取类型、Board、坐标、旋转和尺寸；
- 枚举某类型实例；
- 读取引脚和连接快照；
- 将临时句柄升级为宿主管理的实例引用，或明确拒绝跨帧保存。

### 7.2 生命周期回调

按需要提供：

- `on_create` / `on_destroy`；
- `on_clone`；
- `on_board_enter` / `on_board_leave`；
- `on_move` / `on_rotate` / `on_resize`；
- `on_config_changed`；
- `on_compile` / `on_compile_failed` / `on_unbind`；
- `on_simulation_start` / `on_pause` / `on_reset` / `on_stop`；
- `on_load` / `on_save`。

回调失败必须只禁用目标实例或目标元件类型，不让异常越过 C ABI。

### 7.3 状态种类

宿主区分：

1. **配置状态**：电路设计的一部分，复制和存档时保留；
2. **仿真状态**：寄存器、计数器等，重置时清空或恢复初值；
3. **可选持久运行状态**：RAM、终端历史等，由类型明确声明是否保存；
4. **渲染资源**：纹理和 Surface，只在运行时存在；
5. **临时缓存**：不参与复制、撤销和存档。

状态由宿主分配、限额和释放。第一版可采用有上限的 blob；后续再增加分页存储，不把任意插件指针写进
存档或 Undo 记录。

## 8. 仿真与组合电路

### 8.1 仿真阶段

必须支持 `COMPILE`、`RESET`、`CYCLE`、`REFRESH`、`START`、`PAUSE`、`STOP`。按证据决定是否增加：

- `INPUT_CHANGED`，只在输入变化时调用；
- 上升沿/下降沿订阅；
- `schedule_wakeup(cycle)`，给定周期再次调用；
- 同类型批量回调，减少跨 ABI 成本。

统计延迟与真实周期延迟必须是两个独立声明：前者影响分数，后者由宿主调度输出提交。不能继续把
“声明延迟 5”误解成输出会自动延后 5 周期。

### 8.2 内部网表

`tc.component.compose` 负责：

- 按稳定类型 ID 创建内部节点；
- 连接内部引脚；
- 设置内部参数；
- 导入已有 `circuit.data`；
- 校验悬空、位宽、多驱动和组合环；
- 嵌套其它 Mod 元件；
- 返回依赖清单和编译诊断。

内部节点由宿主持有，插件不接触游戏序列地址。原版节点用稳定语义 ID 查询，再由当前构建画像映射到
真实 kind。

### 8.3 原版复用

明确提供三条不同路径：

1. `clone_builtin_metadata`：只复制名称、图标、引脚和可复制字段，不承诺行为；
2. `create_builtin_node`：在组合电路里使用原版元件，由游戏正常编译；
3. `register_builtin_alias`：外层实例仍进入原版完整分发路径，保留特殊绘制与交互。

每个原版类型应报告 `LOGIC`、`STATE`、`RENDER`、`INPUT`、`EDITOR`、`SERIALIZE`、`ALIASABLE`
等能力位。不能完整别名的类型必须明确返回不可用，而不是退化成只有外观的空壳。

## 9. 存档、复制和编辑事务

### 9.1 存储契约

`tc.component.storage` 提供：

- 配置序列化/反序列化；
- 可选运行状态序列化；
- schema 迁移；
- 复制语义；
- 数据校验；
- 大小查询和配额错误。

宿主在记录写入前完成序列化，在保存失败时不覆盖原数据。字符串、数组和 blob 的所有权在 ABI 中逐项
写清。

### 9.2 缺失和升级

电路文件至少保存 Mod ID、类型 ID、schema 版本、引脚快照、配置 blob 和可选状态 blob。缺少 Mod 时：

- 显示带诊断信息的占位元件；
- 保留原坐标、旋转、尺寸和连线锚点；
- 不参与仿真，或按显式默认值输出；
- 原样保留未知 blob；
- 安装对应 Mod 后尝试恢复。

迁移失败时保留旧数据并报告，不自动写回损坏版本。

### 9.3 编辑事务

配置、尺寸、旋转、引脚变化和内部资源变更必须进入游戏撤销系统。目标是每次玩家确认操作对应一条
Undo；批量工具可显式开启、提交或放弃一个事务，不能用帧间隔猜分组边界。

这部分依赖现有删除、移动和撤销分组研究，在对应命令稳定前不得宣称编辑器集成完成。

## 10. 棋盘绘制和几何

### 10.1 绘制回调

至少提供：

- 元件栏图标；
- 放置预览；
- 棋盘本体背景、主体和覆盖层；
- 选择、悬停、错误状态；
- 属性面板预览。

`TCComponentRenderContext` 应包含实例句柄、局部到棋盘/屏幕变换、包围盒、旋转、缩放、裁剪矩形、
主题、选择状态和只读引脚值快照。

第一版只暴露宿主绘制原语和资源句柄：线、矩形、圆、多边形、文字、SVG、图片、UV 和裁剪。不要让
公开契约绑定当前 OpenGL/ImGui 的私有结构。

### 10.2 资源生命周期

- 创建、更新、释放都由渲染线程执行；
- 实例销毁、离开 Board、设备丢失和 Mod 失败时自动回收；
- 资源句柄按 Mod 和实例隔离；
- 限制纹理尺寸、数量、总字节和每帧命令数；
- 提供设备重建通知，不允许插件长期保存 renderer 原生 ID。

## 11. 输入、焦点和跨线程通道

### 11.1 元件输入

`tc.component.input` 负责局部命中测试和事件路由：

- 指针进入/离开、移动、按下、释放、点击、双击、滚轮和拖动；
- 物理键、扫描码、修饰键、重复；
- Unicode 字符、IME 组合和提交；
- 请求/释放鼠标捕获；
- 请求/释放键盘焦点；
- 事件是否被消费，是否继续交给棋盘快捷键。

事件同时给出屏幕、棋盘和元件局部坐标。焦点实例销毁、离屏或切场景时由宿主自动清理。

### 11.2 跨线程通道

`tc.component.channel` 至少提供：

- render → simulation 的实例消息队列；
- simulation → render 的设备命令队列；
- 双缓冲只读快照；
- 容量、丢弃策略、序号和统计；
- 实例 generation 校验；
- 非阻塞提交和拉取。

队列不能传插件栈地址或游戏对象裸指针。实例销毁后，宿主按 generation 丢弃迟到消息。

## 12. Keyboard 参考实现

### 12.1 需要的接口

- 允许一输入、多输出或按原版原型别名；
- 每实例键盘焦点；
- 物理键、扫描码、字符和修饰键事件；
- 输入消费和游戏快捷键隔离；
- render → simulation 队列；
- 输出脚的原子更新；
- 失焦、重置、暂停和切场景处理；
- 可选的按键/字符队列配置存档；
- 棋盘本体焦点、按键和错误提示绘制。

### 12.2 验收场景

1. 放置两个 Keyboard，点击其中一个后只有它收到字符；
2. 输入 ASCII、方向键、修饰键和重复按键，输出脚与界面显示一致；
3. 输入框有焦点时，Delete/R 等棋盘快捷键不误触发；
4. 切换焦点、暂停、重置、离开关卡后没有残留按键；
5. 保存、重开、复制、撤销和重做不混淆实例；
6. 同一输入序列重复运行得到相同电路输出；
7. 原版 Keyboard 别名与原版本体在相同场景下行为一致。

## 13. Screen 参考实现

### 13.1 Framebuffer 服务

`tc.device.framebuffer` 至少支持：

- 创建、销毁和调整 Surface；
- 1 位、索引色、RGB/RGBA 等协商格式；
- 调色板；
- 清屏、整图上传和脏矩形更新；
- 最近邻/线性过滤；
- 双缓冲和 `present`；
- 绑定到元件局部矩形；
- Surface 状态查询、配额和设备重建。

仿真线程只写命令或宿主映射的 CPU 缓冲；GPU 上传和绘制留在渲染线程。

### 13.2 验收场景

1. 注册 3 输入、0 输出的 Screen 并正常放置、连线和编译；
2. 电路按地址/数据/写入信号更新像素，棋盘本体显示与期望 framebuffer 一致；
3. 缩放、平移、旋转、选择和裁剪时画面位置正确；
4. 两个 Screen 使用独立 Surface，销毁其中一个不影响另一个；
5. 高频写入不会阻塞仿真线程，脏矩形和队列溢出有诊断；
6. 重置、离开关卡、设备重建和插件失败后无资源泄漏；
7. 配置保存并恢复；若声明保存 framebuffer，则像素内容也按策略恢复；
8. 原版 Screen 别名与原版本体在相同输入下显示一致。

## 14. 属性编辑器和棋盘集成

`tc.component.editor` 应支持声明式属性 schema 和可选自定义绘制：

- bool、整数、枚举、颜色、字符串和位宽；
- 校验、预览、确认和取消；
- 右键菜单和工具提示；
- 双击动作；
- 调整尺寸手柄；
- 修改可能断线时的确认；
- 一次确认写一条 Undo；
- Copy/Paste 与 Duplicate 调用定义好的 clone 语义。

完整棋盘集成还依赖稳定的删除、移动、选择、高亮和镜头接口。它们可以由现有命令/计划逐步补齐，
但在参考外设只需放置、交互和保存时，不应阻塞前面的绘制、输入和 framebuffer 研究。

## 15. 诊断、配额和权限

### 15.1 诊断

必须能定位到 Mod、类型和实例：

- 注册和依赖失败；
- 编译失败；
- 引脚宽度和连接错误；
- 未写输出；
- 回调超时或异常；
- 错线程调用；
- 队列积压和丢弃；
- 状态、Surface、纹理和存档配额；
- 资源泄漏；
- 原版别名在当前构建不可用。

开发接口应能查看实例状态、引脚值、回调次数、耗时、内部网表和资源占用，并允许导出波形或诊断报告。

### 15.2 配额

在实现前为下列项目确定默认值和错误码：

- 每 Mod 类型数和每类型实例数；
- 每实例配置、仿真和持久状态大小；
- 每 Mod 总状态大小；
- Surface 最大尺寸、数量和总显存；
- 每帧绘制命令数；
- 每实例消息队列容量；
- 存档 blob 大小；
- 回调时间告警阈值。

### 15.3 权限

全局键盘、剪贴板、任意文件、网络、麦克风和外部程序属于单独权限。Keyboard 元件默认只接收游戏
窗口内、宿主路由给该实例的输入，不因此获得系统级键盘监听权限。

## 16. 分阶段实施

### 阶段 0：原版外设研究与契约前置

目标：确认原版 Keyboard/Screen 的真实分发路径，避免基于 Prototype 形状设计错误接口。

工作：

- 探测 `0x5d Keyboard` 的输入来源、焦点、字符队列、生成代码和保存字段；
- 探测 `0x5b Screen` 的仿真写入、像素存储、棋盘绘制和资源生命周期；
- 确认特殊行为按 kind、原型、编译节点还是 presenter 分发；
- 确认原版别名能否保留真实 kind，或需要宿主包装分发；
- 确认棋盘坐标、相机、旋转、裁剪和命中测试上下文；
- 输出独立研究交接和真机日志，不新增公共 ABI。

退出条件：两类元件从“信号进入”到“仿真/绘制/输入结果”的调用链都有可复现证据；无法稳定接入的
部分明确标记为不可用或需要替代实现。

### 阶段 1：Registry、Pin 和 Signal V2

目标：先解决 Screen 无输出、源元件无输入、固定数组和稳定 pin ID。

交付：

- `tc.component.registry` V1；
- `TCComponentTypeDefinitionV2`；
- 可变长 pin/value buffers；
- 0 输入/0 输出支持；
- 类型查询、依赖和错误模型；
- 旧 `register_component` 适配层。

验收：0→1 常量源、1→0 Sink、超过 8 个引脚和超过 64 位信号通过离线与真机测试，旧 byte-adder
行为不变。

### 阶段 2：实例、状态和生命周期

目标：移除固定 `state[8]` 和固定状态槽依赖，建立可靠实例所有权。

交付：实例句柄、生命周期、宿主状态 blob、重置语义、资源归属、失效规则。

验收：多实例计数器、创建/销毁/复制/重置、旧句柄拒绝和宽输出压力用例通过；不再依赖固定
`0x9a0000` 状态槽作为公共契约。

### 阶段 3：存储、迁移和编辑事务

目标：元件配置与状态可安全保存，缺少 Mod 时不丢数据。

交付：storage 服务、schema 迁移、占位元件、复制语义、Undo 快照。

验收：保存→重启→读回；升级 schema；卸载 Mod 后保存再恢复；复制和撤销保持正确实例数据。

### 阶段 4：组合电路与原版复用

目标：让 Mod 明确选择复制元数据、内部复用或完整别名。

交付：稳定原版类型目录、内部网表 builder、嵌套依赖、`register_builtin_alias` 可行路径。

验收：原版 AND 内部节点、嵌套 Mod、状态元件组合以及至少一个普通原版别名真机通过；特殊外设别名
是否可行由阶段 0 的证据决定。

### 阶段 5：棋盘绘制、几何和资源

目标：元件能在棋盘本体上绘制稳定内容。

交付：geometry/render 服务、宿主绘图原语、局部变换、裁剪、预览和资源生命周期。

验收：自定义 LED/七段显示器在移动、旋转、缩放和裁剪场景下像素回读正确，离开关卡后资源归零。

#### 阶段 5 的需求与接口草案（2026-09-22，由文本框元件实测得到）

参考元件：`examples/text-box`（0 脚装饰元件，板上自绘文本框）。它是阶段 5 的第一个真实使用
者，下面每一条都来自真机测量，出处见 [research/text-component.md](research/text-component.md)
与 [research/component-appearance.md](research/component-appearance.md)。

已测到的三处缺口（三条互相独立的证据）：

| 缺口 | 证据 | 结论 |
|---|---|---|
| 元件在板上的占位由游戏固定给出（约 1–2 板面单位），**不跟内部电路走** | ① compact（内部 9 单位宽）与 wide（117 单位宽）的 32×32 设计图逐字节相同；② 用"放置重叠"判据扫描，两种形状被拒绝的范围一样；③ `update_custom_design` 把内部电路**自动缩放**进 32×32 格 | "占位"可以声明；但"整框可拖"要的是**命中**几何，而两者不是一回事，且见第 5 节：现有命中读数不可信，先解决测量 |
| 游戏给自定义元件画的"设计图 + 名字水印"无法按类型关闭 | 名字设成空格可去水印、`shape_svg` 无影响；空电路定义可以让游戏完全不画，但那个元件同时失去可点区域 | "可见性"与"占位"必须**分开声明**：能隐藏 ≠ 能控制占位 |
| 插件直接改原型字段/设计图内存不安全 | 写入 `+0x368`/`+0x508` 或 `+0x570` 指向的缓冲区后，游戏在加载期直接退出（`fault.log` 无记录） | 外观写入必须由**加载器**走游戏自己的代码路径（`update_custom_design` 那条链），不能暴露裸偏移 |

接口草案（V1，只覆盖"让文本框这类元件成立"所需的最小面）。2026-09-22 的第一刀已经
交付 `set_footprint` + `read_footprint`；当前构建唯一已验证可安全写入的是原型的局部矩形序列，
因此已发布 V1 先采用**单一 footprint**，没有冻结一个无法独立兑现的 `set_hit_box`。放置/占位
路径已真机确认；**命中路径仍未定位，原来的否定证据也不够**：旧探针用 `SetCursorPos` 驱动真实
光标、按下前也不 hover，测试期间的真实鼠标动作会把采样点顶掉（离元件 40 格的空点也读成已选中，
多次运行的网格互相矛盾）。装置改成"先 hover + `ClipCursor` 钉住光标 + 逐点 `clean` 标记"后，
旧的两点结论可以复现，但只有两点；而且只按下不移动的手势整窗读 0，说明读数对手势敏感、整张命中
图还没跑出来。命中盒只有在做出干净的全网格读数之后，才以新服务版本追加：

```c
/* tc.component.geometry V1：类型声明自己在棋盘上的占位与命中。 */
#define TC_SERVICE_COMPONENT_GEOMETRY "tc.component.geometry"
#define TC_COMPONENT_GEOMETRY_API_VERSION_1 1u

typedef struct TCComponentGeometryApiV1 {
    uint32_t size, version;
    void* context;
    /* 声明 type 的棋盘占位：以元件坐标为中心的矩形，单位是板面格。
       host 负责把它写进游戏自己的原型/棋盘路径（不是让插件改内存）。 */
    int (*set_footprint)(void* context, uint64_t custom_id,
                         float half_width, float half_height);
    /* 读取游戏当前真正使用的占位（真机断言用，不经插件缓存）。 */
    int (*read_footprint)(void* context, const TCGameHandle* component,
                          float* half_width, float* half_height);
} TCComponentGeometryApiV1;

/* tc.component.render V1：类型接管自己的棋盘绘制。 */
#define TC_SERVICE_COMPONENT_RENDER "tc.component.render"
#define TC_COMPONENT_RENDER_VERSION_1 1u

typedef struct TCComponentRenderFrameV1 {
    uint32_t size, version;
    TCGameHandle component;
    uint64_t custom_id;
    uint64_t instance_id;
    /* 局部 -> 屏幕：与游戏自己的 world_pos_to_screen_pos 同一变换，
       宿主算好给插件，插件不需要再解相机。 */
    float origin_x, origin_y;      /* 元件中心在屏幕上的像素 */
    float units_to_pixels;         /* 一倍板面格 = 多少像素（含 DPI/缩放） */
    float clip_min_x, clip_min_y, clip_max_x, clip_max_y;
    const uint8_t* config;         /* 该实例的配置 blob（可为空） */
    uint32_t config_size, config_schema;
    void* draw_api;                /* 宿主绘图原语表，后续与 tc_ui_draw 对齐 */
} TCComponentRenderFrameV1;

typedef struct TCComponentRenderV1 {
    uint32_t size, version;
    void* context;
    /* 关掉游戏默认绘制：设计图缩略图 + 名字水印。按类型生效。 */
    int (*set_default_drawing)(void* context, uint64_t custom_id, int enabled);
    /* 每帧回调；只在关卡里、仅对该类型实例调用。 */
    int (*set_draw_callback)(void* context, uint64_t custom_id,
                             void (*draw)(void* user, const TCComponentRenderFrameV1*),
                             void* user);
} TCComponentRenderV1;
```

语义与验收（每一条都要有真机用例，不接受"看起来对"）：

1. `set_footprint` 之后，"放置重叠"扫描能测到新的矩形；鼠标命中的一条判据要先做出**可靠且灵敏**
   的读数（要求：隔离真实鼠标输入并逐点标记污染、同点重复一致、含一个已知必中的正向对照点），
   再在同一隔离用例里量到新矩形；
2. `set_default_drawing(id, 0)` 之后，该实例在板上**不出现任何游戏像素**（像素回读验证），
   而占位/拖动/选中/删除仍按 `set_footprint` 的矩形工作——这正是文本框要的"整框可拖 + 隐形"；
3. 旋转 90°/180°/270°、缩放与平移下，插件绘制的矩形与命中盒保持同向；
4. 离开关卡后回调停止、宿主借出的指针全部失效（与 `tc.component.instances` 同规则）；
5. 不声明 geometry 的类型行为与今天完全一致（旧插件零改动）。

实现顺序（每步一个真机用例）：geometry（声明 + 读取）→ render（默认绘制开关 + 绘制回调 +
宿主变换）→ 文本框迁移过去当参考元件 → 阶段 6 的 input（把手拖动、整框拖动不与框选冲突）。

**为什么先 geometry 再 render**：文本框现在最大的痛点是"整框拖不动"，而它只依赖占位；
绘制接管可以稍后跟上，两者分开以后，"可见性"和"占位"也不再互相绑架。

## 18. 主要风险与决策点

| 风险 | 处理 |
|---|---|
| 原版特殊外设严格按内置 kind 分发 | 阶段 0 先验证；必要时把“完整别名”实现为宿主代理，不伪造普通 Custom kind |
| 棋盘绘制缺少稳定插入点 | 先做只读变换与受控绘制探针；固定构建画像失败时服务不暴露 |
| 仿真线程与渲染线程竞争 | 宿主队列/双缓冲；禁止插件直接跨线程访问资源 |
| 大状态拖慢 Undo 和存档 | 明确上限、可选持久化、脏页/增量方案后置 |
| 动态引脚造成导线丢失 | 配置事务先报告断线集合，确认后单条 Undo 提交 |
| 原版类型 ID 随构建变化 | 公共语义 ID + 每构建映射表，未知时返回 unavailable |
| Native Mod 崩溃无法真正沙箱隔离 | 回调边界捕获可捕获错误、禁用实例；文档继续声明同进程权限风险 |
| 完整接口一次设计过大 | 服务拆分、参考元件驱动；没有实际消费者的扩展不提前冻结 ABI |

以下决策必须在对应阶段开始前记录：

1. 类型 ID 使用字符串、64 位数还是二者组合；
2. 多字信号的字节序和对齐；
3. 配置/状态 blob 的最大尺寸；
4. 原版别名是否保存原 kind；
5. 动态引脚断线的确认与无 UI 路径；
6. framebuffer 支持的第一批格式；
7. Keyboard 是否默认消费所有键，还是只消费字符键；
8. 外设状态是否默认进入电路存档。

## 19. 不纳入首个完成版本

以下能力可以沿同一架构扩展，但不作为 Keyboard/Screen 闭环的阻塞项：

- 任意网络、文件系统和外部进程访问；
- 麦克风、摄像头和系统级全局键盘监听；
- Shader 自定义和任意原生 GPU 命令；
- 跨平台支持；
- 无重启热卸载 DLL；
- 多人同步；
- 完整音频外设。

这些项目若进入范围，必须单独补权限、资源和确定性设计。

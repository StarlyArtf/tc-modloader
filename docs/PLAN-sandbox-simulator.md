# 计划：沙盒独立仿真器（对标真实数字电路仿真器）

日期：2026-09-25。状态：**S2 已完成**（离线内核、沙盒网表、槽位写回与自主推进均有回归）。
构建：该指定构建（EXE 基址 `0x140000000`，引擎 `tc_game_engine.dll` 基址 `0x180000000`）。
范围：沙盒里**不再执行游戏编译出来的仿真程序**，改由本工程自己的事件驱动仿真器推进电路；
游戏负责编辑、绘制、存档与生命周期。

> 一句话：把"游戏的编译器 + 它的定步仿真"换成"我们自己的网表化 + 事件驱动仿真内核"，
> 按真实数字仿真器的方式建模——四态值与强度解析、整数时间单位、分层事件队列与 delta 环、
> 惯性延迟、每时序弧/每边沿的延迟、setup/hold 检查、VCD 观测。元件语义、导线、槽位写回、
> 绘制与存档仍与游戏共用同一份数据。

## 0. 定位：与既有做法的关系

既有做法是**改写游戏发射的源码**，在它的单位循环里插延迟发布（现已归档到 [unused/gate-delay](../unused/gate-delay/README.md)）。
它的全部复杂度来自"必须让游戏的编译器产出能跑的程序"：剪开/接回、`LATE` 守卫、两个 cycle body、
单一时间所有者、按 kind 查延迟、每单位全状态快照。

本方案一次性放弃这条约束：**我们不跑游戏编译出来的程序**，因此上面这些机制一件都不需要。
同时它也放弃"延迟数值仍由现表决定"的渐进路线——延迟作为**可加载的时序库数据**进入设计。

保留的只有安全与边界：只在沙盒生效、设置页可关、开关关闭时与未装 Mod 逐字节一致、
不改存档格式、不改分数口径、不接管 `sim.do` 的"推关卡输入 / 判定结果"角色。

## 1. 为什么值得重做

| 现做法的天花板 | 原因 | 新设计的答案 |
|---|---|---|
| 时间是"一周期 K 个单位"的整数格 | 调度与游戏周期绑定 | 整数时间单位（默认 1 单位 = 1024 刻度），周期只是换算点 |
| 只有单值延迟 | 一个元件一个数 | 每**时序弧**（输入脚 → 输出脚）、每**边沿**（tplh/tphl）、可选 min/typ/max |
| 只有传输延迟 | 队列到期必落地 | 默认**惯性延迟**（Verilog `assign #d` 语义）+ 脉宽滤波；transport 可显式切 |
| 毛刺只有"到达先后" | 没有 delta 环 | 分层队列 + delta 环：零延迟器件、同刻多级收敛是真语义 |
| 环必须剪开再接回 | 游戏编译器拒绝环 | 环是一等公民（本来就没有"编译"这一步）；穿自定义元件的环同样成立 |
| 多驱动只有"短路检测" | 值是单驱动假设 | 四态 + 强度解析：多驱动网按强度表解析，冲突给 X |
| 没有不定态 | 只有 0/1 | `X` 是一等值：未初始化、冲突、亚稳采样都显示为 X |
| 没有 setup/hold | 时序元件只按周期锁存 | 寄存器有 setup/hold/clock-to-q 弧，违例可上报并可视化 |
| 观测只能逐周期 | 采样点在生成程序里 | 逐事件 + VCD 导出，外部波形工具可读 |

## 2. 对标：真实仿真器有什么，我们怎么落

| 真实仿真器概念 | 参考语义 | 本设计的落点 |
|---|---|---|
| 时间精度 / 分辨率 | Verilog `timescale` | 整数刻度：1 单位 = 1024 刻度（`TC_SIM_TICKS_PER_UNIT`），周期 = K 单位 |
| 分层事件队列 | active / inactive / NBA / monitor | 时间轮（可跳过空时刻）+ 三层队列 + delta 环 |
| delta 环 | 零延迟迭代到收敛 | 同一时刻的事件成批收敛，不推进时间 |
| 惯性延迟 | `assign #d` 默认，窄于 d 的脉冲被吞 | 默认档；队列里"未到期条目被新值取代" |
| 传输延迟 | `assign #d transport` | 可选档 |
| 时序弧 | cell 的 `(A→Y)` 弧 + tplh/tphl | 时序库每条弧一组值 |
| 负载 / 转换时间 | NLDM 表（input slew × output load） | 可选扩展：库文件支持 `(slew, load) → delay` 表；不启用时退化为常数 |
| SDF 反标 | 后仿把真实延迟写回网表 | 时序库是**外部数据文件**，可由 `.lib` / SDF / 实测生成 |
| 四态 | 0 / 1 / X / Z | 值系统一等公民 |
| 强度解析 | wired-and / wired-or / 冲突给 X | 多驱动网的解析表 |
| setup/hold | 建立/保持检查 + notifier | 寄存器弧检查，违例计数与上报 |
| VCD | 波形转储 | 导出 VCD，直接喂 GTKWave；与既有 `local.scope` 的 VCD 能力同格式 |
| 器件模型 | primitive + UDP | 器件库：行为（组合函数/时序状态机）与弧表分离 |

## 3. 架构

```text
        simcore/   （纯 C++，零游戏依赖，可独立运行）
   ┌──────────────────────────────────────────────────────┐
   │ L0 值系统   4 态 + 强度解析（0/1/X/Z，驱动强度表）      │
   │ L1 时间     整数刻度，事件 (time, seq) 全序            │
   │ L2 调度     时间轮 + active/NBA 分层 + delta 环         │
   │ L3 器件库   行为（组合/时序）+ 时序弧 + setup/hold 检查  │
   │ L4 网表     net / pin / 弧连接 / 扇出 / 多驱动          │
   │ L5 观测     逐事件 trace、VCD 导出、违例报告            │
   └──────────────────────────────────────────────────────┘
                    ▲                        │
     tcsim/（游戏适配层）                      │
     ┌──────────────┴───────────┐            ▼
     │ 网表构建：编译期扁平序列 → L4 │   槽位写回：我们的值 → 游戏状态缓冲
     │ 槽位表：元件节点槽 + 导线槽    │   控制：推进/暂停/单步（tc.simulation）
     │ 原生回调：自定义逻辑元件       │   门控：只在沙盒 + 开关开
     └──────────────────────────┘
```

**关键分界**：`simcore/` 不知道游戏存在，因此可以在游戏外跑（离线单测、批量仿真、
与 iverilog 交叉验证、CLI 出 VCD）；`tcsim/` 只做两件事——把游戏的数据变成网表，
把结果写回游戏的槽位。

## 4. 语义规格

### 4.1 值系统（L0）

- 值：`0` / `1` / `X`（不定）/ `Z`（高阻）。位向量按位独立解析，net 解析后再做位运算。
- 强度：至少实现 `strong` / `weak` / `highz` 三档（够表达多驱动与三态）。解析规则按标准表：
  同向同强度 → 该值；同向不同强度 → 强者胜；反向同强度 → `X`；无驱动 → `Z`。
- 与游戏显示的关系：游戏状态槽是字节，所以 `X`/`Z` 需要在**写回层**映射成玩家看得懂的表示
  （建议：`X` → 该槽写 0 但登记为违例并在棋盘上高亮；`Z` → 同上，标为"未驱动"），
  具体做法在 S4 与绘制一起定，不在内核里妥协。

### 4.2 时间（L1）

- 时间 `t` 是 64 位整数刻度；`1 单位 = 1024 刻度`；周期 = `K 单位`（K 仍默认 8）。
  精度可调（`TC_SIM_TICKS_PER_UNIT`），刻度只影响分辨率，不影响语义。
- 所有延迟、建立/保持窗口都以刻度表达；时序库里的"单位"是显示单位，加载时换算。
- 一次 `advance(target)` 不跨周期边界（周期边界是"锁存点"），保证寄存器/延迟线/RAM 的
  锁存相位与关卡侧读数稳定。

### 4.3 调度（L2）

- 队列：**时间轮**（延迟有上界，O(1) 插入弹出）+ 溢出最小堆（无上界时回退）。
- 分层：`active`（组合求值）→ `NBA`（时序元件更新，Verilog 的非阻塞赋值语义）→
  `monitor`（观测/断言）。寄存器用 NBA 更新，避免"同一时刻读到新值"这类经典错误。
- delta 环：同一时刻的所有 active 事件处理完仍产生新事件时，在同一时刻再来一轮，
  时间不前进；环上限（如 1000 轮）触发"零延迟振荡"报告——这是真实仿真器都会报的错。
- 排序：`(time, 层, seq)`，同刻同层按插入序（稳定、可复现）。

### 4.4 延迟模型（L3 的一半）

- **默认惯性**：器件在 `t` 求值出 `v`，若该输出在 `t+d` 之前又被求值成别的值，前者撤销；
  输入脉冲窄于 `d` 时输出不产生脉冲（脉宽滤波）。这是 `assign #d` 的语义，也是让毛刺看起来
  像硬件的关键一条。
- **transport 可切**：需要"看毛刺怎么传"的教学场景保留该档。
- **时序弧**：延迟按 `(输入脚, 输出脚)` 索引，而不是按元件；每条弧有 `tplh` / `tphl`
  （上升沿/下降沿不同），可选 `min/typ/max` 三档（默认 typ）。
- **库是数据**：时序库是外部文件（JSON 或 SDF 子集），加载时绑定到器件类型。
  没有库条目时退化为"每器件一个常数"。

### 4.5 器件库（L3）

- 行为与弧分离：行为是纯函数或状态机，弧只描述时间。
- 组合：`NOT/NAND/NOR/AND/OR/XOR/XNOR`（含 3 输入）、`Mux`、比较器、加法器/移位/CLZ/CTZ/
  乘除、Splitter/Maker/Concatenator——位数按游戏原型的引脚字宽。
- 时序：寄存器（`D → Q`，setup/hold/clock-to-q）、计数器、延迟线、RAM（地址建立、
  数据输出）、端口（Load/Store port）。
- 三态/双向：开关、被驱动网的 `Z`（游戏里 `Switch`/`Switched Input` 这类有对应物）。
- IO/外设：关卡 IO（沙盒里没有）、Screen/Keyboard/Time 等按"游戏侧仍是真值源"的方式桥接
  （我们的值是影子，游戏侧读写仍走它自己的入口）。
- **自定义元件**：来自网表的展开（见 4.6），与内置器件同一条路径。
- **原生逻辑回调**：由 C++ 决定行为的自定义元件，在我们的器件库里注册成一个"宿主器件"，
  每次求值调用回调（相位语义沿用既有 SDK）。

### 4.6 网表（L4）

- 来源有两条，主路径由 S0 第 6 项定：
  - **A 编译期扁平序列**：`add_circuit_code` 第 2 参数（长度 `+0`、数据 `+8`、步长 `0x238`；
    自定义元件的内部节点带 `+0x18` = 父实例，见
    [research/component-pipeline.md](research/component-pipeline.md:725) 与
    [src/native_logic.hpp:1406](../src/native_logic.hpp:1406)）。代价：它只在**游戏编译**时出现，
    而带环的板子编译不了——所以这条路的形态是"剪一份无环副本编译一次，只为拿网表与槽号，
    拿到就丢掉发射结果"，剪开仍然存在，但只是**取数**手段，不再影响行为。
  - **B 自己递归读定义**：板子记录（元件 kind/坐标/旋转/自定义原型 id）+ 原型引脚几何 +
    自定义元件的定义文件（`circuit.data`）逐层展开。完全不触发游戏编译，代价是要自己解析
    定义文件并处理定义变更/缓存。
- 两条都要加上板子的导线表（`board +0x98/+0xa0`：两端点 `+0x18..0x1e`、位宽 `+0x30`、
  状态槽 `+0x38`，见 [src/board_objects.hpp](../src/board_objects.hpp)）。
- 引脚几何：原型表锚点 `+8`，相对坐标 `+2`、字宽 `+0x10`；旋转取元件记录 `+0x06`。
  125 个内置原型的引脚与字宽已可 dump（`build/kinds.txt`），坐标重合的引脚**不猜**（既有规则）。
- 展开：自定义元件按扁平序列展开到叶子器件；实例内部网表由此获得（板级记录本身没有父链，
  见 [research/board-object-fields.md](research/board-object-fields.md:10)）。
- 环：不需要剪开——引擎直接处理反馈；这也是本方案取消剪开/接回的**唯一依据**。
- 多驱动：一个 net 的多个驱动在解析层处理，不再只报 `short_circuit`。

### 4.7 观测（L5）

- 逐事件 trace（时间、net、值、原因：哪个器件的哪条弧）。
- **VCD 导出**：时间刻度直接是 VCD 的 timescale；既有 `local.scope` 已经有 VCD 导出，
  同一格式即可对接外部波形工具。
- 违例报告：setup/hold、多驱动冲突、零延迟振荡、未驱动网——按器件/网络聚合，供 S4 做可视化。

## 5. 与游戏的边界（谁拥有什么）

| 关注点 | 归属 | 说明 |
|---|---|---|
| 编辑、选择、撤销、存档 | 游戏 | 一概不动；不改存档格式 |
| 棋盘绘制、导线着色 | 游戏 | 读**状态缓冲**里的槽位——就是我们要写回的那套坐标（[sdk/simulation.md](sdk/simulation.md:154)） |
| 示波器 / 逐周期采集 | 游戏 + Mod | `tc.sim.capture` 现在靠"在生成程序里插 tick"；本方案由我们直接喂，且可做**亚周期**采集 |
| 电路求值（组合/时序） | **我们** | `simcore/` |
| 周期语义 | 我们 | 周期边界 = 锁存点；`cycle` 计数通过既有 `simulation_settings` 写回 |
| 推进 / 暂停 / 单步 | 我们（经 `tc.simulation`） | 既有 slice 机制可用（`src/sim_control.hpp`） |
| 关卡判定 / 分数 | 游戏 | 沙盒没有判定；非沙盒一概不走本方案 |
| 原生逻辑回调 | 我们调用 | 器件库里的"宿主器件" |

**槽位写回**是唯一新增的硬契约，也是 S2 的核心风险：必须写全**元件节点槽 + 每根相连导线的槽**
（既有经验：同一个值会被发射器写进元件自己的槽和它每根导线的槽；旧实测记录保存在 [门级延迟归档](../unused/gate-delay/README.md)）。

### 6.1 结论（2026-09-25，真机）

第 1、3、6 项已经有证据，第 2、4、5 项仍未做。证据来自 `tests/sim-state-probe.cpp` 的
`TC_SIM_STATE_DEEP` / `TC_SIM_STATE_WRITE` / `TC_SIM_STATE_DRIVE` 三个开关（只读探针 + 一次
显式写回实验），报告写在 `build/state-map.txt`，板级记录被
[tools/extract-board-fixture.ps1](../tools/extract-board-fixture.ps1) 固化成
[tests/data/and_gate-board.txt](../tests/data/and_gate-board.txt)。

| # | 结论 | 证据 |
|---|---|---|
| 1 | 元件记录的 `+0x30` 是**输入脚数**、`+0x40` 是**输出脚数**（与原型表逐个对上：Input 0/2、AND 2/1、Output 1/0）；`+0x38` 是游戏自己的私有指针（0 输入元件为空，其余指向一个首字等于脚数的结构），**不是**状态槽 | `deep_component` 的 `word@0x30/word@0x40` 与 `build/kinds.txt` 的原型脚数一致 |

| 6 | **走 B（自己从记录构建网表）**：拿真板的 6 个元件 + 3 根导线，用游戏自己的原型表取引脚几何，构建出 nets=3、devices=1、sources=2、observed=1、unconnected_pins=0、fatal=0 的网表，和电路本身完全一致；A（剪副本编译取槽号）降级为退路 | `drive` 报告的 `netlist` 行；离线回归 `simcore` 用例用同一份记录断言同样的结果 |

## 8. 验证策略（不允许自证）

1. **器件级单测**：每个器件的真值表 + 每条时序弧（含 tplh/tphl 差异、X/Z 输入）。
2. **外部裁判**：网表导出成 Verilog（每个器件一条 `assign #(tplh,tphl)`，时序元件用
   `always @(posedge clk)` + 显式窗口），用 **iverilog** 跑同一激励，比对逐事件波形。
   这是本方案最重要的验收手段——"我们的仿真器对不对"不该由我们自己说了算。
3. **退化对拍**：把延迟全设 0（或全设 1 单位）并关掉惯性滤波，此时引擎的周期边界读数应当
   与游戏自己的仿真一致——用于兜住"开关关闭/无延迟时行为不漂移"。
4. **极限场景**：奇数反相环（振荡频率 = 环长 × 每级延迟）、对称锁存（亚稳 → X）、
   多驱动冲突（→ X）、三态网（无驱动 → Z）、零延迟环（报振荡而不是死循环）。
5. **真机回归**：沿用既有的 ring/latch/clock/两 NAND/编辑生命周期用例；读数口径不变
   （`changed slots`、稳态值、`flag`、编译计数），只是这次由我们的引擎产生。

1. 只在**沙盒**生效；设置页开关默认关；**开关关闭时与未装 Mod 逐字节一致**；

## 14. S2 进展（2026-09-25）

S2 最危险的两个未知——"网表能不能只从记录构建"和"我们写的槽游戏认不认"——已经在真机上得到
答案（§6.1 第 3、6 项），代码落在 `simcore/include/tcsim/board.hpp`：

- `readBoard()`：按已验证的字段摆放解出元件记录与导线记录（kind/x/y/rotation/id/custom、
  脚数、端点、位宽、状态槽）；
- `buildNetList()`：把引脚几何（来自游戏自己的原型表）旋转到位、用并查集把导线连成网、
  把引脚挂到网上、把 wire 的 `+0x38`（及其相邻字节）记成该网的写回槽，并把
  Input/Button 这类标成"由游戏状态数组驱动"（`source_nets`）、Output 这类标成"游戏要读回来"
  （`observed_nets`）；
- 未支持的种类、脚数与原型不一致、两个引脚占同一格，全部进 `notes` 并且**不猜**；
  标了 `fatal` 的网表不允许运行（红线 6）。

离线回归用真机 dump 固化的记录跑同一个构建器（`simcore` 用例的最后一段）：3 根导线 → 3 个网、
槽 256/257、258/259、260/261，AND 接对 A/B/Y，两个 Input 网是 source、输出网是 observed，
三处重合格被报出来。

真机实验（`TC_SIM_STATE_DRIVE=1` + `TC_SIM_STATE_INVERT=1`）走完了整条路：读板 → 构建网表 →
按游戏槽喂源 → 跑我们的事件驱动引擎 → 把**我们**的值写回状态数组 → 用游戏自己的读取器读回来。
故意写反值时读回的就是反值（`program=1 read=0`），说明槽的所有权在我们手里；同时也量到
游戏程序会在同一周期把它自己的值写回去，所以写回必须发生在游戏推进之后（或把程序的求值抑制掉）。

这条路的可复用部分已经收进 `simcore/include/tcsim/runtime.hpp`（`SandboxRuntime`）：
它拿"板级记录 + 引脚几何"，管三件事——周期换算（1 周期 = `cycle_units × 1024` 刻度）、
每周期把游戏状态数组里的源喂给引擎、引擎收敛后把每个网的字节（wire 的 `+0x38` 及其相邻字节）
写回。`publish()` 与 `stepCycle()` 分开，正是为了配合"必须在游戏推进之后写"这个真机结论，
也为了让所有权实验（写反值再看读回）能成为一条正式断言。离线回归用真机固化的那块板跑通了
两拍：两个输入一低一高时输出网读 0，两高时读 1，源网的字节保持不变，写反值时输出字节跟着反。

### 14.1 S2 中途清单（历史记录）

**先记已经做完的**：正式 Mod 落在 `examples/sandbox-sim/plugin.cpp`（包名 `dev.sandbox-sim`，

   别名槽"的真身。and_gate 板整份写回表是
   `{262} {263} {256,257} {258,259} {260,261}`：三根导线各自的槽组正好是

   自己两个输入脚的节点槽（单槽节点，由游戏当源驱动，不是我们的写回目标）。
   证据固化在 `tests/data/and_gate-stores.txt`，离线回归 `simcore` 里有一段拿它和板级记录
   对拍：三根导线的写回集合与程序真的写入的槽组逐一对上。
   **仍未验证**：带环的板子游戏不给编译，也就没有发射源码可查别名组；那种板上我们只能按
   "wire 的 `+0x38` 与 `+0x38+1`"写（本板上三种导线全部成立），需要在 S3 用一块真环板确认；

`tests/sandbox-sim-ring-playtest.ps1` 把**闭合的三 NAND 环**（`build/sandbox_sim_ring_closed_board.data`，
玩家画法：环在记录里是闭合的）注入沙盒，装上 `dev.sandbox-sim` 跑一次。结果：

- **我们的构建器确实看见了环**：`bound board -> nets=6 devices=3`，六根导线（三根环线 + 三根观察线）
  连成六个网，三个 NAND 变成器件；另外三个种类是 `0x46 Switched Output`（观察用的沉，已补进
  `kindIsSink`）。**网表是从记录建出来的，跟游戏编译与否无关**；
- **游戏给不出 tick**：探针请求 `run` 之后日志是 `timed out waiting for cycle 1 current=0`，
  随后板子被重置（我们再次绑定时 `nets=0`）。也就是说：**游戏编译不了的板子，游戏也不会推进它的 cycle**，
  所以"让游戏推进、我们在它之后覆盖"这条现在走的路，对带环板根本不成立；
- 结论：S2 剩下的**推进控制不是可选项**。要跑环振/锁存这类旗舰场景，就必须由我们自己驱动 cycle
  （经 `tc.simulation` 的 slice/run 或直接推进我们自己的时钟），同时守住红线 4：不接管关卡输入与判定，
  只在沙盒且开关打开时接管。

### 14.3 推进控制（进行中）

已实现：`dev.sandbox-sim` 的配置里加 `free_run=N` —— 每 N 个渲染帧推进一个引擎周期并写回，
**不看游戏的 cycle**（`free_run=0` 是默认，行为与之前一致：跟着游戏 cycle 走）。方向是"我们自己的时钟"，
守住红线 4：沙盒里跑图纸，关卡输入与判定仍归游戏。

**卡住的一步，以及它说明的事**：在闭合环那块板上跑 `free_run=2` 时，板子先是绑定成功
（`nets=6 devices=3`），编译失败后又被重置成空板（`nets=0`），而**我们的报告一次都没写出来**——
说明那种状态下渲染帧回调根本没被调用（游戏在一个编译失败的板子上不再出帧）。所以后面的推进要挂在
**还能跑的地方**：已经加入的 `sim.do` 链（在仿真线程上、与渲染无关），而不是 `on_frame`。

**新的授权与下一步**：业主已明确"必要的话可以动 cycle"。于是推进控制的目标定为：
1. 用一次只读探针找到 model 里的 cycle 字段（`sim_get_cycle` 读的那个数），用"已知 cycle 值 + 走一拍看谁 +1"确认；
2. 在 `sim.do` 链节里推进：调用我们引擎的一个周期 → 写回槽位 → 把游戏 cycle +1，
   让示波器/采集/周期显示都跟着我们的仿真走（红线 4 只管"不接管关卡输入与判定"，cycle 不在其列）；
3. 复验环板：槽里出现周期 = 环长 × 每级延迟的振荡——那才是 S2 的旗舰验收。

### 14.4 推进控制（2026-09-25 达成）

1. **cycle 不在 model 里**：只读探针 `TC_SIM_STATE_CYCLE=1` 扫了 model 首页所有对齐 u64，
   结论 `cycle_field none: no aligned word in the first page tracked the cycle`——计数器不在

### 14.5 S2 完成（2026-09-25）

S2 的四条验收路径已成为正式回归，不再是诊断脚本：

1. `sandbox-sim`：真实沙盒里的 AND 板从板记录构建为 `nets=3 devices=1 sources=2 observed=1`，
   自主推进并写回 256/257、258/259、260/261；`-Invert` 证明非源槽读到的是我们发布的反值；
2. `sandbox-sim-latch`：两 NAND + 三个常量从闭合记录直接建成 `nets=4 devices=5`，最终稳定保持
   `n0=1 n1=0 n2=1 n3=1`；
3. `sandbox-sim-ring`：三 NAND + 三个常量建成 `nets=6 devices=6`，第一次求值后显式种一个未知网，
   边间隔恒为 `3 × 8 = 24` tick，同值完整周期为 48 tick；游戏不能编译该板也不影响推进；
4. `sandbox-sim-clock`：按 `+0x188` 解析宿主 Clock 原型，由自主 cycle 驱动事件源，Clock 与第一层
   NOT 都逐周期翻转，后者精确落后 8 tick；槽位同步供棋盘、探针和 scope 的既有读取路径使用；
5. `sandbox-sim-disabled`：`enabled=0` 在解析状态、注册 level/sim/cycle hook 和安装 frame callback 前
   直接返回；真机日志确认零行为 hook、零状态报告，关闭时没有第二个状态所有者。

这轮同时修正了三个真机才暴露的问题：`0x2e` 是带设置值的 Constant（不是 Switched Output）；
标量驱动宽网必须按引脚规则扩展而不能丢弃；失败编译清空 simulation model 时，只要编辑器仍显示同一
块非空板，接管模式要保留最后一个有效绑定。未知普通自定义元件仍按红线 6 致命拒绝；S2 只为已注册的
宿主 Clock 建立了明确行为，通用自定义定义递归展开继续属于后续器件覆盖工作。

### 14.6 值到颜色的通路，与"没有索引的导线"（2026-09-25）

**通路（反汇编 + 真机，不是推测）**

- 每帧 `render_component_snapshots__main_u414` → `update_tbo_sim_state__presenterZupdate95state95stream_u1315`：
  整个函数只有五条指令，把 `simulation_state__modelZsimulator95types_u81` 指向的 **0x9c4000** 字节
  原样上传成一张 GPU TBO（这个长度就是插件里的 `state_size`）。
- 每根导线的顶点属性里只有**一个索引**：`push_tbo_wire_segment__presenterZupdate95state95common_u1170`
  调 `get_state_index__modelZsave95mongerZcommon_u5502`（RVA `0x1400c7c70`），把返回的 32 位值拆成
  四个字节写进顶点，着色器按 `TBO[index]` 取字节决定颜色。`get_state_index` 的语义是**字节偏移**：
  `sim_state_read_u64__modelZsimulator95types_u159`（RVA `0x14010f2e0`）就是 `*(u64*)(simulation_state + index)`。
- 循环依赖检查（`find_circular_path__modelZsimulationZpreorder_u27493`、
  `set_circular_dependency__modelZsimulationZpreorder_u27466`，同在 `model.simulation.preorder`）
  **不参与渲染**：它只发生在关卡加载/编译那一步，而上面那趟 TBO 上传每帧无条件执行。它对渲染的唯一
  实际伤害是"没跑完 preorder 就没有给导线分配索引"。
- 真机对照一（AND 板，`invert=0/1` 各跑一次同一块板）：引脚点、导线端点圆点、导线中间那截小色条在
  粉红(0) ↔ 绿(1) 之间翻转，说明颜色跟的是我们发布的字节。
- 真机对照二（闭合三 NAND 环，`-NoSeed -FreeRun 60` 让状态稳定，`invert=0/1` 两张截图逐像素比较）：
  导线上 **2997 个像素**随发布值翻转，报告里每个网自己的槽字节同步翻转。证据图
  `build/render-probe-out/ring-steady-{0,1}.png`、`and-{normal,invert}.png`。

**问题：没有索引的导线**

- 导线记录 `+0x38` 起是 0x18 字节的状态描述符，实测两种形状：**已分配** = `{index, 1, 0}`
  （如 256/258/260/262/264），**未分配** = `{1, 256, 1}`，`get_state_index` 对后者返回 **1**。
- 闭合环真机：被 cycle-unblock 临时切断以让编译器通过的那根闭环线 `(-21,-1)->(22,0)` 正是未分配的
  那根，其它五根都拿到了真实索引；更早（unblock 之前）的读数里六根导线记录全部停在 1，
  **六根不同的导线共用同一个字节**。
- 后果：这些导线的颜色不是它自己的值；多根导线还会争同一个字节（写回"后写的赢"）。

**修法**（`examples/sandbox-sim/plugin.cpp`）

1. **自己拥有索引**：`ensureWireStateIndices` 取一根游戏分配过的导线描述符作模板，只改前 8 字节的偏移，
   **用游戏自己的 `get_state_index` 回读确认**之后才写回记录（真机日志：
   `wire 0 had no state index (resolved 1); gave it 4194304`）。模板跨板缓存，供"整块板一根都没分配"
   的情况使用；私有块默认 `0x400000`，只有当设计自己用到那一带时才退到高水位 `+0x1000`。
2. **切回边不再越界**：回边只允许活在需要它的那一趟编译里——新的 wire-copy 开始前、
   `set_circular_dependency`（编译器判定有环，也就是那一趟的终点）时、preorder 之后、`level.load`、
   `sim.do` 与每帧回调都会还原，另有 250 ms 看门狗；日志里的
   `cycle-unblock cut outlived its compile pass; restored` 就是看门狗收的尾。
3. 报告新增 `patched_wires=` / `patch_base=`；回归脚本新增两条硬断言——**任何网都不得写到 `< 256`
   的占位字节**，**导线表形状不得在会话中途变化**。

**顺带量到的两件事**

- `unblock=0`（配置项，`tests/sandbox-sim-ring-playtest.ps1 -NoUnblock`）照样跑通环板并给出 24 tick
  边间隔：索引由我们补齐后，cycle-unblock 不再是渲染或推进的前提，它现在只决定"游戏自己那份 shadow
  程序是否存在"。
- 补的索引**不进存档**：补过索引的那次运行写出的 `circuit.data` 里搜不到 `0x400000`（游戏自己的存档
  格式是 v16，描述符是运行期数据）。

**仍未做**

- 导线表在会话中途被重写（真机上见过一次：一根带拐角的长导线被拆成四条记录、新记录没有索引）还没有
  根因结论；现在的兜底是"形状一变就重绑 + 补齐索引"，并且回归会拒绝这种变化。
- 像素验收目前只在"值稳定"的场景做过（`-NoSeed -FreeRun 60`）；振荡相位与截图的对齐还没做成断言。
- 待定：是否把 cycle-unblock 默认关掉（`unblock=0`），彻底不碰游戏的编译图。

### 14.7 子周期发布：让周期内部的脉冲看得见（2026-09-25）

**症状**：玩家搭的边沿检测（时钟 → NOT → AND）在沙盒里"没有反应"。

**量到的原因**：引擎侧本来就是对的——`sandbox_sim_edge_detector_board.data` 的 trace
（该 fixture 原先漏画了时钟→NOT 那根线，NOT 输入悬空，已修）：

```text
t=638976 net=0(时钟)→1
t=638984 net=1(NOT 输出)→0        （晚 8 tick，= 门延迟）
t=638984 net=2(AND 输出)→1
t=638992 net=2→0                  （脉冲宽 8 tick）
```

而一个周期是 `cycle_units × ticks_per_unit = 8 × 1024 = 8192` tick，**发布只在周期边界做一次**，
所以宽度 8 tick 的脉冲永远落在两次采样之间：报告里 `n2` 恒为 0，棋盘上也就永远看不到。

**改法**（`simcore/include/tcsim/runtime.hpp` + `examples/sandbox-sim/plugin.cpp`）：

- `SandboxRuntime::advance(ticks, read_source)`：推进任意 tick 数，**只在跨周期边界时**给源网与时钟网
  赋新值。整周期调用与旧的 `stepCycle()` 逐事件等价（`stepCycle()` 现在就是
  `advance(cycleTicks)` 的包装，离线 197 项断言与真机四条回归都未变）；
- `stepTicksFor(steps)` 把"每周期发布 N 次"换算成每步多少 tick；
- 配置新增 `steps_per_cycle`（默认 1 = 旧行为）。插件按步推进并在**每一步之后发布**，历史行按发布
  计数（同一周期内多行 `history cycle=` 是正常的）；`cycles_run` 现在读运行时的周期计数，而不是步数。

**验收**（真机，`tests/sandbox-sim-ring-playtest.ps1 -Circuit edge`）：

| 配置 | 结果 |
|---|---|
| 默认（`steps_per_cycle=1`，`gate_delay=8`） | 24 行发布里 `n2=1` **一次都没有**（脉冲不可见，复现症状） |
| `-StepsPerCycle 8 -GateDelay 1024`（门 = 1 单位，每单位发布一次） | **1/24 行**看到 `n2=1`（脉冲进入发布流），断言通过 |

也就是说：要让脉冲"看得见"，两个旋钮要一起用——门延迟调成 1 单位（`gate_delay=1024`），发布粒度
调到 1 单位（`steps_per_cycle=8`）；脉冲宽度恒等于一级门延迟，所以想让它更宽就得在延迟路径上多串几级
（这是电路设计，不是仿真器的事）。这条已登记为 `sandbox-sim-edge`（game 层）。

#### 14.7.1 采样相位：第一次的量法是错的（2026-09-25 当天修正）

第一版结论写的是"`steps_per_cycle=8` 时 1/24 行能看到脉冲"。玩家报告"上升沿检测永远不输出高电平"，
复查后确认那句话**是采样点撞上的巧合，不是稳定现象**——而且报告本身还在吃证据。两点都修了：

1. **采样相位**：脉冲相对周期边界的相位是 `[+1 个门延迟, +2 个门延迟)`（时钟上升 → 门延迟后 AND 上升
   → 再一个门延迟后 AND 下降；脉冲起点 = `t0 + D`）。子步长恰好等于脉冲宽度时，采样点正好落在脉冲的
   两个端点，结果全凭边界开闭；重现量到：

   | 配置 | 一个上升沿落在发布行里的次数 |
   |---|---|
   | `gate_delay=1024`（脉冲 1024 tick），`steps_per_cycle=8`（子步 1024） | 1 行（恰好落在脉冲起点） |
   | `gate_delay=1024`，`steps_per_cycle=16`（子步 512 = 脉冲一半） | **2 行（稳定）** |

   规则：**子步必须小于脉冲宽度**（取一半就稳），即 `cycle_ticks / steps_per_cycle < 脉冲宽度`。
   脉冲宽度由延迟路径决定（玩家在设计里控制：延迟路径串 k 级，脉冲就是 k 个单位宽），所以推荐
   `gate_delay=1024` + `steps_per_cycle=16`；想让它看起来是"闪一下"而不是一帧，再把 `free_run` 加大
   （每个子步占 `free_run` 帧）。
2. **报告窗口**：`history` 原先只留最后 24 行，而 `steps_per_cycle=32` 时一个周期就是 32 行——脉冲行
   （周期内第 5~9 个子步）**永远被截掉**，报告里看起来"从来没有高电平"。现在至少保留四个周期的行数
   （`max(24, steps*4+8)`），并且每行带 `t=<engine tick>`，可以直接和 trace 事件对齐。

**能不能"用"**：脉冲宽度 = 一级门延迟。后面接**需要两个门延迟才能建立**的门级主从结构时，这个脉冲
本来就太窄（这是模型的物理，不是 bug）；要靠它捕获，要么把延迟路径串到 2~3 级让脉冲变宽，要么等内置
Register（边沿触发原语）实现——那正是 14.6 结尾列的 A 项。

### 14.8 自锁开关：交互元件的值不在状态数组里（2026-09-25）

**症状**：砂盒里点自锁开关（`local.clock` 的 `SWIT_001`）没有任何反应。

**根因（读代码 + 真机对照）**：开关的值由**元件自己的实例配置**保存——点击处理里
`storeInteractiveLevel` 把 level 写进 `tc.component.storage` 的配置字节，然后
`publishInteractiveLevel` 调 `component_instances.reset` 刷新回调绑定；而把回调输出**搬进
`simulation_state`（元件节点槽与导线槽）的是游戏编译出来的程序**。砂盒恰恰把那个程序停掉了
（`stock run suppressed`），所以导线槽永远停在开机时的值：`addStimulus` 每次读到的都是 0。
（真机日志里点击本身是生效的：`interactive: applied ... level=0/1` 在翻，但状态数组不动。）

**修法**：

- 网表为每个源网记下"它由哪个宿主元件驱动"（`BuildResult::SourceOrigin{custom_id, instance_id}`，
  与 `source_nets` 一一对应；内置源——关卡输入、Verilog Input——保持 `custom_id == 0` = 读状态数组）；
- 插件通过 `tc.component.instances` 枚举 `SWIT_001`/`BUTN_001`，用
  `tc.component.storage.read_config` 读每个实例的第 1 个配置字节（就是点击写进去的 level），
  每帧刷新一次，作为该源网的值；`mod.json` 的能力里因此加了 `component`；
- 诊断开关 `interactive_level=0|1`：按点击的同一条路径（写配置 + reset 实例）强制电平，供无鼠标
  注入的回归使用。

**验收**（真机，`tests/sandbox-sim-ring-playtest.ps1 -Circuit switch -InteractiveLevel N`，
板子 `switch -> NOT -> NOT`，net0 是开关的网）：

```text
[dev.sandbox-sim] sandbox-sim: interactive 0x9c5 level=0 (from its own configuration)
[dev.sandbox-sim] sandbox-sim: interactive level forced to 1 on 1 instance(s) (click-equivalent write + reset)
[dev.sandbox-sim] sandbox-sim: interactive 0x9c5 level=1 (from its own configuration)
interactive switch: configured level 1 reaches the engine as net0=1 and net1=0
```

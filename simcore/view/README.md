# simcore-view —— simcore 自己的窗口

独立进程，**不连游戏**。读一份板子记录，问 simcore 的网表构建器"这块板子是什么"，
可选地让 simcore 的引擎跑一遍，然后用 Win32 GDI 画出来。

它存在的理由只有一个：**这是另一套渲染管线。** 游戏那边是 ImGui，这里是 GDI，
两边没有共同祖先。所以当游戏的棋盘和这张图对同一个值给出不同答案时，那个分歧是信息，
不是渲染噪声——这正是分辨"游戏渲染问题还是 simcore 问题"需要的东西。

## 自己打开

**双击 `simcore/view/open.cmd`。** 没编译过它会先编译，然后打开反相环那个演示。
带参数可以换板子：

```cmd
open.cmd --board data\latch.txt
open.cmd --board data\and_gate.txt --bmp out.bmp
```

也可以直接跑 `build\simcore-view.exe`：**不带参数启动会弹一个文件选择框**，
挑一个板子记录就行。带了板子名的话，会按"当前目录 → exe 目录 → 源码目录"的顺序去找，
所以在哪启动都不影响：

```powershell
.\build\simcore-view.exe --board ring3.txt     # 从任何目录都能找到 simcore/view/data/ring3.txt
```

## 随沙盒自动打开

`dev.sandbox-sim.mod` 已内置 `simcore-view.exe`。启用 sandbox simulator 后进入沙盒，插件会先写出
`sandbox-sim-board.txt`，再自动启动随包 viewer：

```text
simcore-view.exe --board <插件数据目录>\sandbox-sim-board.txt --watch
```

窗口每 200 ms 跟随记录变化；已经开着时不会重复启动，关闭后下次进入沙盒会重开。
`sandbox-sim.txt` 中写 `view=0` 可禁用，`viewer=<绝对路径>` 可覆盖随包版本。

窗口分四块：**工具栏**、**板面**、**右侧面板**、**状态栏**。

| 操作 | 效果 |
|---|---|
| 点元件 / 导线 | 右侧列出它的 net、当前值和写回的状态字节（点空白处取消） |
| 滚轮 | 以光标为中心缩放 |
| 按住拖动 | 平移；按了没动就算一次点选，所以两个手势共用左键 |
| `Space` | 换下一个输入组合（latch 会翻转） |
| `R` / `F` | 输入组合复位 / 缩放到适应 |
| `O` | 打开另一个板子 |
| `S` / `B` | 存 SVG / 存一张整窗的 BMP |
| `+` / `-` | 放大 / 缩小 |
| `L` | 切换"整理"排布（见下） |
| `Esc` | 退出 |

工具栏上每个按钮都有对应的键，不用记也行。状态栏给缩放比例、光标所在的板面坐标，
以及光标底下是什么。

## 命令行

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File simcore/view/build.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File simcore/view/tests/view-tests.ps1

.\build\simcore-view.exe --board simcore\view\data\ring3.txt              # 开窗口
.\build\simcore-view.exe --board simcore\view\data\ring3.txt --svg out.svg
.\build\simcore-view.exe --board simcore\view\data\ring3.txt --bmp out.bmp
.\build\simcore-view.exe --board simcore\view\data\ring3.txt --no-window --ticks 400
```

离线用例挂在 `tests/test-catalog.json` 的 `simcore-view`（fast 层），随套件一起跑：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/test.ps1 -Tier fast -Name 'simcore*'
```

它断言的是**查看器自己那层**：夹具格式、引脚几何、格子到像素的映射、点选落在哪个元件或
哪根线上、net 到写回槽的对应、SVG 的形状。另外钉住两条这张图依赖的语义——三反相环真的振荡
而不是停在 X，交叉耦合 NAND 在输入组合变化时真的翻转。这些都不需要 GDI，所以它们在任何能
编译 simcore 的地方都能跑。

| 参数 | 说明 |
|---|---|
| `--board FILE` | 板子记录（格式见下）；省略时弹文件选择框 |
| `--svg OUT` | 同一份图元列表写成 SVG |
| `--bmp OUT` | 把**整个窗口**（工具栏＋板面＋面板＋状态栏）离屏渲染成 BMP，板面 1:1 且不随当前缩放平移变化 |
| `--ticks N` | 引擎跑到第 N 个刻度，默认 200 |
| `--size WxH` | 初始窗口尺寸；默认按板子和面板的需要算，保证面板内容不被挤掉 |
| `--tidy` | 用数据流网格排布元件，而不是板面真实坐标 |
| `--select-component N` | 按板子记录里的下标选中一个元件（用于出证据图） |
| `--select-wire N` | 按板子记录里的下标选中一根导线 |
| `--no-window` | 不开窗口，只出文件（脚本用） |

## 点选：这张图从"图"变成"诊断"

一根导线的 net 就是 simcore resolve 出来的结果，而 `slots_of_net` 是这个值**写回游戏状态数组**
的字节位置。把这两个东西放在同一屏上，前面说的三种故障才分得开：

| 看到什么 | 说明 |
|---|---|
| simcore 的值错 | 器件语义或网表构建的问题 |
| simcore 的值对，但写回的槽不对 | 写回层的问题 |
| 两边都对，游戏画面还是错 | 游戏渲染的问题 |

选中一根导线：

```text
wire 2:  12,0 -> -1,1  (1 bit)
  net 2 = 1
  state bytes written: 260 261
```

选中一个元件：

```text
component 1:  AND
  kind 0x04 at 4,0 rot 0 deg
  pins in 2 out 1
  device 0: u1_and2
  in0  -> net 0 = 0
  in1  -> net 1 = 0
  out0 -> net 2 = 0
```

写回槽那一行的空括号是有意义的：`(none: nothing reads this net back)` 表示这根线的值
不会被游戏读到，所以游戏画面看不到它对不上——这本身就是一条线索。

## 随包夹具

| 夹具 | 看什么 |
|---|---|
| `data/and_gate.txt` | 值真的传下去了：Input → AND → Output 三根线同色 |
| `data/ring3.txt` | **游戏会拒绝这块板子**（circular dependency），simcore 跑它，而且三反相环真的在振荡 |
| `data/latch.txt` | 交叉耦合 NAND 锁住状态，按 `Space` 能看到它翻转 |
| `data/mux.txt` | 真机录下来的一条 0x2a Mux 记录：一位选通脚 + 16/32 位数据脚，现在能重放 |

`ring3` 是这三个里最重要的一个：它是"两个仿真器不是同一个东西"的最小证据。
`mux.txt` 不是给人看的演示，是**证据**：它逐字节抄自 2026-09-29 那次沙盒 dump
（`sandbox-sim-board.txt` 的元件 22），所以"一块玩家搭的板子里有 Mux"这件事在离线用例里
也有据可查——在这个文件之前，查看器会因为 `0x2a` 没有器件而整块板子拒跑。

## 板子记录格式

和 `simcore/tests/simcore-tests.cpp` 已经在读的是同一个格式，所以一次捕获可以同时喂给
单测和查看器，不需要第二套格式：

```text
component index=0 kind=0x04 x=4 y=0 rotation=0 word30=2 word40=1 custom=0
wire index=0 from=0,-1 to=3,-1 width=1 slot=256
wire index=1 from=-7,-12 to=-4,-17 width=1 slot=260 path=-7,-12;-4,-15;-4,-17
```

`path=` 是可选的：写出来就是**游戏自己画的那条折线**（绝对板面坐标），查看器照它画、不再自己布线；
没有这个字段的线才走下面那套"七种走法"。沙盒插件（`examples/sandbox-sim`）会把运行时导线记录里的
腿数组换算成这个字段，所以"棋盘上什么样、这张图就什么样"（`docs/changelog.md` 记了那次测量）。

- `word30` / `word40` 是记录里的输入／输出脚数，构建器会拿它和原型的引脚表交叉核对。
- `custom` 可选，只用于 `kind=0x4e` 自定义元件的标签。
- 以 `#` 开头的行是注释。
- **导线的端点必须正好落在引脚所在的格子上**，构建器是靠格子做并查集连网的。

## 画的是什么，不是什么

**是**：每个元件一个矩形 + 元件名；每个引脚一个点；每根导线一条直线；值按四态着色
（0 蓝 / 1 绿 / X 红 / Z 灰）。

**元件体不是固定尺寸，是从引脚推出来的。** 原型表里输入脚在 x = −1、输出脚在 x = +2，
所以"以元件格为中心、固定宽两格"的盒子会**贴着输入、把输出甩出去一整格**——第一版就是
这么画的。现在盒子在**每个引脚前停半格**，两端的引脚都露在外面；引脚全挤在一列上的元件
（Input / Output）再按标签宽度撑开，否则名字会从盒子里溢出来。

**导线是折线，不是斜线。** 每根线先在格子上布好路由，再换算成像素。路由是"生成七种走法、
挑代价最低的"：

1. 两端共行或共列 → 直线；
2. 两个可能的直角折角；
3. 一条从两端元件体外侧绕过去的**上方/下方通道**；
4. 一条**左侧/右侧通道**。

代价函数是这次返工的重点，按权重从大到小：

| 项 | 权重 | 为什么 |
|---|---|---|
| **掉头** | 1000 | 线从输出脚出来、立刻往回走——看着就是断的。这是最主要的问题 |
| 穿过元件体 | 20 | 难看，但比掉头可接受 |
| 与已布好的线同轨道重叠 | 30 | 两根线叠在一起会让人分不清谁接谁 |
| 长度 | 1 | 同等条件下走短的 |

掉头的权重远高于绕路，所以"多走几格但顺"永远赢过"近但折回来"。

引脚法线是从元件体推出来的（引脚在体的哪一侧），不是猜的；引出线段沿着它走一格，
进引脚那一端也一样，所以线总是"从输出脚正常出来、从侧面进输入脚"。

顺带修掉的一个真 bug：**定界必须放在布线之后**。绕行通道会跑到元件和原始端点构成的矩形
之外，之前先在旧范围里换算像素，绕出去的那段会被裁掉。

**重叠的线要看得出来。** 两根线走在同一条轨道上时，先画的那根会被后画的整条盖住——
看起来就像一根线"接到了"另一根上（这正是第一版的问题：绿线走到一半停在蓝线上）。
两条规则解决它：

- **短的线段画在上层。** 按长度降序发射，于是落在长线上的那一小段引脚引出线留在最上面，
  不会被盖掉。
- **每段线带一圈"描边"（casing）。** 在彩色线下面先画一条同色于画布底的、宽 4 像素的线，
  上层的线就会明显压在下面的线之上，而不是和它糊成一条。

描边不是可点选、也不计入线段的东西（`SceneLine::halo`），点选和高亮都会跳过它。

**接在引脚上的线端有一个连接点。** 这是这张图最该一眼回答的问题："这根线到底接上了没有？"
之前的画法是：输入端就是一个 4px 的深灰小点，导线以圆头结束在旁边——**"接上了"和"断在半空"
长得一模一样**。

现在每个落在引脚上的线端都画一个**导线颜色的实心圆点**（半径 5.5），压在引脚标记之上。
读法因此是确定的：

| 看到什么 | 含义 |
|---|---|
| 导线颜色的实心点 | 这一端接在这个引脚上 |
| 只有一个小深灰点 | 这个引脚没接东西 |
| 线端什么都没有 | 悬空端 |

顺带修了一个画序错误：选中高亮原来画在连接点**上面**，5px 的高亮盖住 5.5px 的点，两侧
露出的圆弧看着像箭头——比不画还难认。现在高亮在下面，连接点在最上面。

**导线不做完整避障。** 只有中段的两个折角有得选，所以交叉耦合那种天生要绕的设计仍会
贴着元件走，偶尔还会从元件体上穿过去。这是取舍：真正的迷宫布线是另一个量级的东西，
而这里是示意图不是布线器。描边至少保证"哪根线压着哪根"一眼能看出来。

## "整理"：一个可选的排布

默认关闭，因为**这个视图的价值就在于它和游戏看的是同一块板子**——换成另一套坐标会削弱
这个用途。

打开后（工具栏的"整理"按钮、`L` 键、或 `--tidy`）元件按**数据流**重排：

- 器件按 BFS 距离从"没有被驱动的那些"排起（关卡输入、常量、开关），按层分列；
- 同一列里按玩家原本的上下顺序排；
- 关卡输入在网表里**没有对应器件**（它是外部驱动的），所以单独放到最左一列——否则它下游
  的所有元件都会被当成根，整块板子挤进第 0 列；
- 列距 7 格、行距 5 格，够放最宽的元件体（全加器三格宽）也不会上下压住。

BFS 而不是最长路径，是因为它在这台仿真器接受的环上会终止；完全无源的环（三反相环）就
落在同一列里，看着也合理。

状态栏会写明当前是"原始"还是"整理（非板面真实位置）"。

**不是**：不是游戏的复制品。坐标线性映射，没有美术。

## 引脚几何从哪来

`kind_pins.hpp` 是一张**冻结的表**。在线插件是问游戏自己的原型表（`buildNetList` 收一个
`geometry` 回调就是为了这个），查看器没有游戏可问，所以表里放的是同一份数据：
组合门那几行来自 `tools/generate-gate-pins.py` 对该构建的输出，Input/Output 那两行是
`simcore/tests/simcore-tests.cpp` 在捕获棋盘上量到的。

**表里没有的 kind 不会被猜。** 元件照画，标成琥珀色并写出 kind 号，同时进 notes；
构建器那边会给出 `fatal`，引擎就不跑了。这是计划里的红线 6（不支持的电路要明说）。

**内存那几行是量出来的，不是推出来的**：`0x36 Load port`（3 进 2 出）、`0x38 Store port`
（5 进 1 出，第 5 个输入在 `(-1,0)`——旧的原型 dump 只印前 4 个脚，正好把它藏掉了）与
`0x76 RAM`（**自己一个脚都没有**）来自 2026-09-29 重新 dump 的 `build/kinds.txt`。
RAM 没有脚不是遗漏：游戏自己的原型表就写 0/0，Symphony 那关的棋盘
（`campaign/symphony_6_ram/circuit.data`）也只有两个 RAM、六个 Load port、四个 Store port 和
**零根导线**——内存是透过端口接进来的，导线接的是端口。
RAM 与端口行为现已进入 simcore（见
[../../docs/PLAN-sandbox-simulator.md](../../docs/PLAN-sandbox-simulator.md) §15.3）：查看器能按插座
顺序重放 8/16/32 位访问。当前边界是游戏 `memory_manager` 的初始镜像尚未自动导入。

**字宽 Mux（`0x2a`）同样已支持**（[§16](../../docs/PLAN-sandbox-simulator.md)）：表里那一行
（选通 `(-1,-1)`、A/B `(-1,0)`/`(-1,1)`、输出 `(2,0)`）来自同一份 `build/kinds.txt`，宽度取记录
`+0xe0`（游戏算好的）或数据引脚上最宽的导线。真机记录 `data/mux.txt` 就是这个形状，查看器
现在能重放它而不是报 "no device in the library"。

## 分了三层，是为了能换掉上下两层

```text
board.hpp / buildNetList / Engine        （simcore，不动）
        │
        ▼
scene.hpp      平台无关：网表 + 值 → 矩形/线段/点/文字
        ├──► svg_writer.hpp     → SVG
        └──► win32 GDI 窗口      → 屏幕
```

中间那层是纯数据，所以它能被离线断言、能被写成 SVG、也能换个后端。窗口那层只是一层薄适配，
用 `#ifdef _WIN32` 包着——simcore 主体仍然零依赖。

GDI 和 user32 是 Windows 系统库，不是第三方依赖，所以 simcore 的"能在游戏外编译运行"
这条性质没有被破坏。

## 还没做

- 与游戏采用文件同步而不是进程内耦合：插件持续刷新 `sandbox-sim-board.txt`，viewer 用
  `--watch` 跟随。它不反向修改游戏棋盘。
- 没有 VCD 对拍视图。`tools/simcore-iverilog.ps1` 现在还是文本比对；把 iverilog 的 VCD
  喂进来和 simcore 自己的值并排画，才是"外部裁判"的完全体。
- 点选只给读数，还不能反过来高亮游戏里对应的元件。
